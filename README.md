## 검수 방식

작업 중에는 화면과 코드를 보면서 그때그때 반려했습니다.
잘못 만든 것은 이 단계에서 대부분 걸러졌습니다.

걸러지지 않는 것은 아예 만들어지지 않은 쪽이었습니다.
화면에 나오지 않으니 아무리 봐도 알 수가 없었습니다.
그래서 AI가 작업을 마치고 올리는 완료 보고를 저장소 실측치와 한 줄씩 맞춰봤습니다.
다 했다고 적혀 있는데 실제로는 안 되어 있는 경우가 여기서 나왔습니다.

| 보고 | 실제 | 어떻게 잡았나 |
|---|---|---|
| 할인 페이지 16개 생성 완료 | 14개 | 파일 개수 카운트 |
| 세부 페이지 필터바 32개 전체 제거 | 4개 남음 | 잔존 파일 목록 대조 |
| 신규 JS 4종 추가 | 실제 8종 | 파일 목록 대조 |

앞의 두 건은 8개짜리 반복 작업에서 마지막 항목인 요리·베이킹 계열이 빠진 건데
둘 다 완료로 보고됐습니다. 한 번은 실수지만 두 번이면 패턴이었습니다.
그래서 배치 작업이 끝나면 개수를 세는 걸 절차로 넣었습니다.

```bash
ls category-*-earlybird.html | wc -l   # 8이어야 함
ls category-*-event.html | wc -l       # 8이어야 함
```

곧바로 효과가 있었습니다. 07-31과 08-01은 보고와 실측이 일치했습니다.
뉴스 43 / 34 / 36 / 30 / 30과 합계 173, 중복 진입 파일 5개 삭제, 신규 16종이 그대로 확인됐습니다.

표의 마지막 JS 건은 방향이 반대였습니다. 실제보다 적게 보고했습니다.
`search`·`cart`·`toggle`·`cert` 4종이라고 적혀 있었는데
`auth-modal`·`myclass-tabs`·`order-tabs`·`mag-more`가 같이 들어가서 8종이었습니다.
부풀리든 줄이든 대조는 해야 한다는 결론은 같았습니다.

`main`을 페이지마다 넣을 필요가 있냐고 물은 적이 있습니다. index에만 있으면 되지 않냐는 취지였습니다.
AI가 문서마다 하나씩 필요하다는 표준 근거를 댔고, 맞는 말이라 원안을 그대로 뒀습니다.

반려하지 않은 결정도 지적과 같이 기록에 남겼습니다.

## 접근성과 색상의 차이

| | 07-30 | 08-01 | 08-03 | 08-13 | 08-15 |
|---|---|---|---|---|---|
| `alt` 속성 누락 | 0 | 0 | 0 | 0 | 0 |
| `skip-link` 보유 | 80/80 | 136/136 | 157/157 | 164/164 | 164/164 |
| 페이지당 `h1` | 1개 | 1개 | 1개 | 1개 | 1개 |
| 하드코딩 색상 (16진수) | 2 | 88 | 132 | 6 | 4 |
| 브랜드색 `rgb()` 표기 | 3 | 187 | 73 | 55 | 22 |

접근성 지표는 1페이지에서 164페이지까지 한 번도 어긋나지 않았습니다.
색상은 08-05 일괄 정리로 132건에서 6건까지 줄었다가, 표기 형태를 바꾼 값으로 다시 늘었습니다.

`alt`과 `h1`, `skip-link`는 페이지 생성 템플릿에 포함된 항목들이었습니다.
새 페이지를 만들면 그대로 복제되므로 제가 매번 챙길 일이 없었습니다.
색상은 컴포넌트를 만들 때마다 새로 판단해야 했습니다.
판단이 들어가는 항목은 페이지가 늘어나는 속도를 따라가지 못했습니다.

시맨틱 별칭도 마찬가지였습니다. 열흘 동안 7%에서 움직이지 않았습니다.
참조 총계가 2,094에서 2,330으로 늘어난 만큼 별칭도 146에서 163으로 늘었을 뿐,
새로 만드는 컴포넌트는 계속 원시 토큰을 직접 부르고 있었습니다.

이틀 뒤 별도 회차에서 이 두 축을 한꺼번에 정리했습니다.
`color`는 `text-*`로, `background`는 `surface-*`로 바꾸는 규칙을 속성 문맥으로 정해
957곳을 전환했고 비율은 57.6%가 됐습니다. 색상도 26건까지 줄었습니다.

같은 회차에 W3C 오류·경고를 정리하고 CSS 중복 선언블록 272그룹을 통합했으며,
`?v=1`에 묶여 있던 캐시버스터 370건을 제거하고 `aria-live`를 전역 알림 영역 방식으로 넣었습니다.
컴포넌트마다 흩어져 있던 `prefers-reduced-motion` 11블록도 전역 1블록으로 합쳤습니다.
이미지 328개를 WebP로 바꿔 `assets`를 12MB에서 5.3MB로 줄였습니다.

`prefers-reduced-motion` 통합에서 `!important` 4건이 생겼습니다. 프로젝트 내내 0으로 지켜온 항목입니다.
전역 모션 차단은 개별 컴포넌트의 애니메이션 선언을 이겨야 동작하므로 `!important`가 정석이고,
이 한 블록에만 허용했습니다. 다른 곳은 그대로 0입니다.

## 색상 개수를 세 번 센 이야기

AI가 완료했다고 보고하면 개수를 세서 대조하게 했습니다.
그런데 그 세는 일도 AI가 했고, 무엇을 기준으로 셌는지는 제가 확인하지 않았습니다.
문서에 올라간 하드코딩 색상 집계가 그렇게 나온 숫자입니다.

처음 나온 값은 131건이었습니다. 16진수만 센 결과였습니다.
08-03에 기준을 두 축으로 넓히라고 지시했고, 브랜드색 `rgb()` 표기를 더해 180건이 됐습니다.
그때는 기준이 정리됐다고 봤습니다.

08-05에 일괄 토큰화를 돌린 뒤, 문서에는 "180 → 0 해소"로 기록됐습니다.

08-13에 검증만 하는 세션을 따로 잡아, 저장소를 새로 클론하고 커밋 단위로 되짚어
같은 스크립트로 다시 세게 했습니다. 그 "0건"이 사실과 다르다는 것이 여기서 확인됐습니다.

| | 16진수 | 브랜드 `rgb()` | 합계 |
|---|---|---|---|
| 08-03 | 132 | 73 | 205 |
| 08-05 (정리 직후) | 4 | 78 | 82 |
| 08-13 | 6 | 55 | 61 |

그날 처리된 건 16진수 축뿐이었습니다.
브랜드색 `rgb()`는 73에서 78로 오히려 늘었습니다.

원인은 간단합니다. 08-03에 "뭘 셀 것인가"는 두 축으로 넓혀놓고
정작 결과 검산은 옛날 기준 한 축으로 했습니다.
기준을 넓히라는 지시와, 넓힌 기준으로 다시 세라는 지시는 별개였습니다.
앞의 것만 하고 뒤의 것을 하지 않았습니다.

같은 세션에서 커밋 수도 어긋나 있었습니다.
작업 리뷰 기준으로 집계된 약 338건이 `git rev-list`로는 353건이었습니다.
`style.css` 줄 수도 9,037에서 멈춰 있었고 실제로는 10,174였습니다.

그래서 이 문서의 수치는 전부 저장소를 다시 클론해 커밋별로 되짚어 확정하게 했고,
재현 명령을 같이 적어 누가 다시 세도 같은 값이 나오게 해뒀습니다.

그런데도 같은 일이 또 있었습니다.
이틀 뒤 토큰화 작업에서 첫 집계가 두 번 틀렸습니다.

타이포는 `clamp()` 내부 px까지 세어 40건이라 했는데 유효한 것은 17건이었습니다.
과소와 과대가 한 번씩 나왔습니다. **무엇을 셀 것인지부터 확인하지 않으면 숫자는 양쪽으로 틀립니다.**

## AI가 원인을 잘못 잡은 두 번

검수는 결과물만 보는 것으로 끝나지 않았습니다. AI가 내놓은 원인 진단도 검수 대상이었습니다.
아래 두 건은 AI가 지목한 원인이 틀렸던 경우이고, 방향을 바로잡은 것은 제 쪽 관찰이었습니다.

### 8/10 가로 스크롤

전날 스크롤바를 없애달라고 하자 AI는 `html { overflow-x: hidden }`을 넣어 감췄습니다.
원인을 없앤 게 아니라 증상만 안 보이게 한 조치였고, 그 사실은 문서의 「미해결 항목」에
"원인 제거가 아니라 안전망"이라고 적혀 있었습니다.
어느 요소가 넘치는지 특정하지 않았다는 뜻입니다.

하루 뒤 제가 같은 문제를 다시 제기했습니다.
`hidden`이 적용된 데스크탑 폭에서는 스크롤바가 보이지 않았지만,
375 · 768 · 820 · 1024 · 1280과 폰에서는 그대로 나타났기 때문입니다.
넘침 자체는 없어진 적이 없었습니다.

> "index.html 전체 가로 스크롤이 생겼어. 원인 찾아줘."

전날과 달리 없애달라고 하지 않고 원인을 물었습니다.
감춰둔 것을 종결로 받지 않은 것, 그리고 데스크탑 말고 다른 폭과 폰에서 확인한 것.
이날 제가 한 일은 이 둘입니다. 원인을 짚어준 것은 없습니다.

원인은 접근성 요소였습니다.

```
<span class="a11y-hidden course-card__score">평점 5점 만점에…</span>
  → position: absolute
  → 캐러셀에 containing block(position: relative)이 없음
  → body 기준으로 잡힘 → 캐러셀 overflow-x 클리핑을 벗어남
  → 가로로 스크롤된 카드 위치(~2700px)가 페이지 scrollWidth에 그대로 더해짐
```

1024px에서 `scrollWidth`가 2644로 찍혔습니다.
두 캐러셀(`.course-list--slider` · `.magazine__list`)에 `position: relative` 한 줄을 넣어
절대요소를 안에 가두게 했더니 768 · 1024 · 1280에서 넘침이 0이 됐습니다.

### 8/13 더블탭

> "링크를 두 번 눌러야 이동한다."

AI가 hover 가설을 세웠습니다. 터치 기기에서 첫 탭이 `:hover`로 소비된다는 가정이었고,
이 프로젝트에 `@media (hover)` 가드가 하나도 없다는 걸 근거로 들었습니다.
방어 코드를 두 번 넣었지만 두 번 다 눌러보니 그대로였습니다.

가설을 뒤집은 건 코드 밖에서 나온 관찰이었습니다.

> "GitHub Pages 링크로 열면 한 번에 이동해."

배포본에는 그 hover 가드가 하나도 들어가 있지 않은데 정상이었습니다.
로컬 개발 서버에서만 나던 증상이었고, 넣었던 방어 코드는 `git checkout`으로 걷어냈습니다.

AI 가설이 두 번 다 빗나갔습니다. 그때마다 제가 한 답은 "여전히 그대로다" 한 줄이었습니다.
원인을 짚어주지도, 다른 가설을 제안하지도 않고 결과만 사실대로 알렸습니다.
그 답이 세 번째 시도에서 로컬과 배포본을 갈라 보게 만들었습니다.
고쳤다는 보고를 그대로 받았다면 방어 코드만 늘어난 채 끝났을 것입니다.

```
08-10   증상이 안 보임 → 실제로는 있었다
08-13   증상이 보임    → 실제로는 없었다
```

두 번 다 코드에는 문제가 없었습니다. 확인 환경이 결과를 갈랐습니다.

AI는 자기 진단이 틀렸다는 것을 스스로 알아내지 못했습니다.
같은 가정 위에서 코드를 고치고 다시 완료로 보고했을 뿐입니다.

방향을 바꾼 것은 확인 조건이었습니다.
스크롤바를 감추던 CSS를 지우고 다시 측정하라고 지시한 것, 배포본에서 직접 열어본 것.
둘 다 코드를 건드리는 일이 아니라 **어디서 확인할지를 바꾸는 일**이었고,
AI는 그 두 번 다 시키기 전까지 하지 않았습니다.

## 검수 도구의 한계

앞의 두 건은 확인 조건을 바꿔봐야 원인이 나온다는 얘기였습니다.
그러려면 확인에 쓰는 도구부터 어디까지 믿을 수 있는지 알아야 했습니다.

작업 중에는 개발 환경에 딸린 미리보기 창으로 화면을 확인했습니다.
그런데 이 창은 폭을 768px 이하로 줄여도 페이지에는 1560px 폭인 것처럼 알려줍니다.
화면은 좁아 보이는데 CSS가 받는 값은 데스크탑이라, 모바일에서 실제로 어떻게 보이는지는 알 수 없었습니다.

`getComputedStyle`과 `scrollWidth`로 계산된 값을 직접 뽑으면 구조는 확인할 수 있었지만,
패딩 침범이나 터치 동작처럼 눈으로 봐야 아는 것은 배포본에서 따로 봐야 했습니다.

실제로 미리보기에서는 1열로 나오던 통계 블록이 iOS에서만 3열로 깨진 적이 있습니다.
같은 날 반대 방향 오차인 더블탭 건도 발생했습니다.
한쪽은 도구가 못 잡았고, 다른 쪽은 도구가 없는 결함을 만들어냈습니다.

그래서 반응형 작업에서는 미리보기 확인으로 끝내지 않고, 배포된 사이트를 제가 직접 폰에서 열어봤습니다.
그렇게 해서 미리보기에서 정상이던 것 중 iOS에서만 깨진 건이 세 개 나왔습니다.
FAQ 검색 인풋의 우측 패딩 침범, 중점(`·`)이 안 넘어가는 것, 그리고 통계 블록 3열입니다.

이틀 뒤 접근성 검사 도구를 돌렸을 때도 같은 일이 반복됐습니다.
**axe가 잡아낸 대비 위반 중 약 60%는 실제로는 문제가 아니었습니다.**
어두운 배경 위에 흰 글씨를 올린 곳인데, axe가 배경을 흰색으로 읽어 대비가 부족하다고 판정한 것입니다.
숫자를 그대로 받았다면 멀쩡한 브랜드색을 바꿀 뻔했습니다.
한 건씩 실제 배경색을 확인해 진짜 위반과 잘못 잡힌 것을 나눈 뒤, 세 건만 처리했습니다.

그런데 그날 밤 배포본에 Lighthouse를 돌리자, **같은 성질이 반대 방향으로도 작동한 것이 드러났습니다.**
대비를 올리려고 본문 회색을 어둡게 바꿨는데, 그 변경이 어두운 배경에서는 대비를 6.88에서 3.67로 떨어뜨렸습니다.
axe는 이 회귀를 잡지 못했습니다. 푸터 배경을 흰색으로 읽었기 때문에 통과로 나온 것입니다.

```
없는 위반을 만들어냈다   60%가 실제로는 문제 아님
있는 회귀를 가렸다      다크 11건을 통과로 판정
```

노이즈만 만드는 줄 알았던 성질이 실제 결함을 숨기고 있었습니다.
배포본에서 다시 측정하고 나서야 이 11건을 찾았고, 고친 뒤 접근성 100이 됐습니다.

앞에서 AI의 완료 보고를 실측치와 대조했습니다. 보고만으로는 못 믿기 때문입니다.
그런데 대조에 쓴 도구가 틀리면 그 대조 결과도 못 믿을 값이 됩니다.
미리보기 창만 보고 "반응형 확인했다"고 적었다면, AI의 "다 했습니다"를 그대로 옮겨 적은 것과
결과가 다르지 않았을 겁니다.

## 남은 작업

하드코딩 색상 26건이 남았습니다. 브랜드색 `rgb(22 103 250 / α)` 계열이 22건입니다.

## 정리하면

지적으로 끝나는 문제와 그렇지 않은 문제가 있었습니다.
404 링크는 경로 규칙 하나가 틀린 것이어서 지적 한 번으로 끝났습니다.
색상은 컴포넌트 수만큼 판단 지점이 있어서, 359건 안에 여러 번 지적하고 일괄 정리까지 했는데도 61건이 남았습니다.
지적은 이미 생긴 것만 잡습니다. 생기는 자리가 여러 곳이면 잡는 속도가 생기는 속도를 못 따라갑니다.

08-15에 회차를 따로 잡아 957곳을 전환하고 색상도 26건까지 줄였습니다.
그래도 08-05와 같은 방식이었습니다. 이미 쓰여 있는 것을 한 번에 손봤을 뿐,
다음에 만들 컴포넌트를 검사하는 규칙은 여전히 없었습니다.
두 번 다 그 시점의 코드는 정리됐지만, 다시 늘어나는 것을 막을 방법은 만들지 못했습니다.

지켜진 쪽은 반대였습니다.
164페이지까지 누락 0으로 간 항목들은 한 번도 지적한 적이 없습니다.
착수 전에 페이지 생성 템플릿에 넣어뒀기 때문입니다.
AI는 시킨 것을 할 뿐 빠뜨린 것을 알려주지 않으니,
애초에 빠뜨릴 수 없는 자리에 넣어두는 편이 매번 잡아내는 것보다 확실했습니다.
지적으로 잡는 것보다, 착수 전에 넣어두는 쪽이 사람이 할 일이었습니다.

여기까지는 무엇을 통제할 수 있느냐의 문제였습니다.
남은 하나는 무엇을 믿을 수 있느냐였습니다.

이번에 틀린 것은 AI 산출물만이 아니었습니다.
AI의 완료 보고가 틀렸고, AI의 원인 진단이 틀렸고,
제 문서에 적힌 집계가 틀렸고, 확인에 쓰던 도구가 틀렸습니다 — 미리보기 창이 그랬고 axe도 그랬습니다.
검수는 만들어진 것을 보는 일이 아니라, 맞다고 말하는 근거를 전부 의심하는 일이었습니다.

처음 질문은 대규모 사이트 구축을 AI에 맡겼을 때 품질을 통제할 수 있느냐였습니다.
만드는 일은 맡길 수 있습니다. 무엇이 맞는지 정하는 일과,
맞다고 말하는 근거를 검증하는 일은 맡길 수 없습니다.
