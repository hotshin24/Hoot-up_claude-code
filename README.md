## 무엇을 확인하려던 프로젝트인가

품질을 통제할 수 있는가**를 규명해보고자 했습니다.

만드는 것 자체는 AI가 했습니다. 문제는 만들어진 것이 지시대로인지,
빠진 것이 없는지, 규칙을 지켰는지를 사람이 검수할 수 있느냐였습니다.
16일간 그 절차를 만들고 돌린 기록입니다.

## 역할 분담

### 착수 전에 확정한 것

AI에 구현을 넘기기 전에, 기준이 될 문서와 디자인을 먼저 확정했습니다.

- **사전 PRD v1.0** — 요구사항을 ID로 정의하고, 구현 중 생긴 계획 변경은 전부 변경 ID로 추적
- **Figma 디자인 시스템과 변수 체계** — 원본값 · 역할 이름 · 스케일 3단 토큰 구조를 설계.
  앞선 JW Anderson에서 역할 이름 9개를 선언해놓고 실참조가 0회였던 문제를 알고 있어서,
  이번엔 그 계층을 쓰는 것까지 착수 조건으로 명문화했습니다
- **152강 카탈로그** — 8개 대분류 39개 세부로 짜고, 세부 개수를 4~7로 통제해 메가 메뉴 높이를 맞췄습니다.
  과금 모델(단건 · 구독 · 병행)을 분류 축과 교차시켜 계정 · 장바구니 · 카드 배지까지 같은 규칙이 관통하게 했습니다
- **브랜드 워딩 체계** — 마이 둥지 · 담은 둥지 · 졸업모 · 도토리.
  GNB는 평문, 본문과 푸터는 세계관 병기로 배치 규칙을 나눴습니다
- **접근성 요구사항** — 이미지마다 `alt`, 모든 페이지에 `skip-link`, 페이지당 `h1` 1개를 요구사항으로 정하고
  페이지 생성 템플릿에 넣었습니다. 164페이지까지 누락 0으로 유지된 이유가 여기 있었습니다

### 만드는 동안 한 것

- **지적 359건** — 일자별로 기록하고 표준 위반 · 인터랙션 결함 · 구조 · 데이터 정합성 · 명명 정합성으로 분류
- **규칙으로 되돌리기** — 같은 결함이 세 번 반복되면 개별 수정 대신 규칙을 지목했습니다.
  그 결과로 규칙표 · 커밋 컨벤션(`feat` / `style` / `fix`) · 개수 검증 절차가 문서로 남았습니다
- **지시에 제약 조건을 함께 넣기** — "썸네일 호버 시 1.3배 확대. 단, 감싼 레이아웃은 항상 같은 크기여야 함."
  뒷문장이 없었다면 카드 확대로 그리드가 어긋났을 요청이었습니다
- **범위 축소 결정** — 강의 상세를 152종 만들지 않고 1종으로 줄였습니다.
  구조가 같고 콘텐츠만 다른 페이지라, 복제해도 증명되는 것은 없고 헤더 중복만 15만 줄 늘어날 상황이었습니다.
  대신 카드 904개가 전부 그 페이지에 실제로 도달하는지를 확인했습니다. 인바운드 링크 1,858건입니다
- **기준 재정의** — 반응형 착수 때 브레이크포인트를 767/1279 2단에서 1280 / 768 / 480 3단으로 바꿨습니다.
  1280에서 열이 줄고 768에서 세로로 서고 480에서 아이콘이 되는데, 두 경계로는 이 셋을 못 나눴습니다
- **문서에 적힌 수치까지 재검증** — AI 보고만 대조하고 문서에 남은 집계는 그냥 믿고 있었다는 걸 뒤늦게 알아채고,
  커밋별로 다시 세게 했습니다

### AI가 한 것

HTML · CSS · JS 생성, 그리고 작업이 끝날 때마다 스스로 쓰는 완료 보고.

### 검수도 나눠서 했습니다

무엇을 볼지 정하고, 결과를 판단하고, 반려하는 건 제가 했습니다.
세고 뒤지고 대조하는 실행은 AI에 시켰습니다.
이 문서의 수치도 대부분 제가 직접 센 게 아니라 지시해서 받은 값입니다.

## 검수 방식

만드는 중에 화면과 코드를 보며 즉시 반려했습니다.
잘못 만든 것은 여기서 검출됐습니다.

문제는 아예 안 만들어진 것이었습니다. 화면에 없는 것은 봐도 확인할 수 없었습니다.
그래서 AI가 작업 끝에 쓰는 완료 보고를 실측치와 하나씩 맞춰봤습니다.
다 했다고 적혀 있는데 열어보면 안 되어 있는 경우가 여기서 나왔습니다.

| 보고 | 실제 | 어떻게 잡았나 |
|---|---|---|
| 할인 페이지 16개 생성 완료 | 14개 | 파일 개수 카운트 |
| 세부 페이지 필터바 32개 전체 제거 | 4개 남음 | 잔존 파일 목록 대조 |
| 신규 JS 4종 추가 | 실제 8종 | 파일 목록 대조 |

앞의 두 건은 8개짜리 반복 작업에서 마지막 항목인 요리·베이킹 계열이 빠진 건데
둘 다 완료로 보고됐습니다. 한 번은 실수지만 두 번이면 패턴이었습니다.
그래서 배치 작업이 끝나면 개수를 세는 걸 절차로 넣었습니다.

```bash
ls category-*-earlybird.html | wc -l   # 8이어야 함
ls category-*-event.html | wc -l       # 8이어야 함
```

곧바로 효과가 있었습니다. 07-31과 08-01은 보고와 실측이 일치했습니다.
뉴스 43 / 34 / 36 / 30 / 30과 합계 173, 중복 진입 파일 5개 삭제, 신규 16종이 그대로 확인됐습니다.

표의 마지막 JS 건은 방향이 반대였습니다. 실제보다 적게 보고했습니다.
`search`·`cart`·`toggle`·`cert` 4종이라고 적혀 있었는데
`auth-modal`·`myclass-tabs`·`order-tabs`·`mag-more`가 같이 들어가서 8종이었습니다.
부풀리든 줄이든 대조는 해야 한다는 결론은 같았습니다.

`main`을 페이지마다 넣을 필요가 있냐고 물은 적이 있습니다. index에만 있으면 되지 않냐는 취지였습니다.
AI가 문서마다 하나씩 필요하다는 표준 근거를 댔고, 맞는 말이라 원안을 그대로 뒀습니다.

반려하지 않은 결정도 지적과 같이 기록에 남겼습니다.

## 접근성과 색상의 차이

| | 07-30 | 08-01 | 08-03 | 08-13 |
|---|---|---|---|---|
| `alt` 속성 누락 | 0 | 0 | 0 | 0 |
| `skip-link` 보유 | 80/80 | 136/136 | 157/157 | 164/164 |
| 페이지당 `h1` | 1개 | 1개 | 1개 | 1개 |
| 하드코딩 색상 (16진수) | 2 | 88 | 132 | 6 |
| 브랜드색 `rgb()` 표기 | 3 | 187 | 73 | 55 |

접근성 지표는 1페이지에서 164페이지까지 한 번도 어긋나지 않았습니다.
색상은 08-05 일괄 정리로 132건에서 6건까지 줄었다가, 표기 형태를 바꾼 값으로 다시 늘었습니다.

`alt`과 `h1`, `skip-link`는 페이지 생성 템플릿에 포함된 항목들이었습니다.
새 페이지를 만들면 그대로 복제되므로 제가 매번 챙길 일이 없었습니다.
색상은 컴포넌트를 만들 때마다 새로 판단해야 했습니다.
판단이 들어가는 항목은 페이지가 늘어나는 속도를 따라가지 못했습니다.

시맨틱 별칭도 마찬가지였습니다. 열흘 동안 7%에서 움직이지 않았습니다.
참조 총계가 2,094에서 2,330으로 늘어난 만큼 별칭도 146에서 163으로 늘었을 뿐,
새로 만드는 컴포넌트는 계속 원시 토큰을 직접 부르고 있었습니다.

## 색상 개수를 세 번 센 이야기

AI가 낸 완료 보고는 매일 대조시켰습니다. 정작 문서에 적혀 나온 집계는 기준을 한 번도 확인하지 않았습니다.

처음 나온 값은 131건이었습니다. 16진수만 센 결과였습니다.
08-03에 기준을 두 축으로 넓히라고 지시했고, 브랜드색 `rgb()` 표기를 더해 180건이 됐습니다.
그때는 기준이 정리됐다고 봤습니다.

08-05에 일괄 토큰화를 돌린 뒤, 문서에는 "180 → 0 해소"로 기록됐습니다.

08-13에 검증 세션을 따로 열어, 저장소를 새로 클론하고 커밋 단위로 되짚어
같은 스크립트로 다시 세게 했습니다. 그 "0건"이 사실과 다르다는 것이 여기서 확인됐습니다.

| | 16진수 | 브랜드 `rgb()` | 합계 |
|---|---|---|---|
| 08-03 | 132 | 73 | 205 |
| 08-05 (정리 직후) | 4 | 78 | 82 |
| 08-13 | 6 | 55 | 61 |

그날 처리된 건 16진수 축뿐이었습니다.
브랜드색 `rgb()`는 73에서 78로 오히려 늘었습니다.

원인은 간단합니다. 08-03에 "뭘 셀 것인가"는 두 축으로 넓혀놓고
정작 결과 검산은 옛날 기준 한 축으로 돌렸습니다.
기준을 고치는 일과 그 기준으로 다시 세는 일은 별개인데 같은 일로 착각했습니다.

같은 세션에서 커밋 수도 어긋나 있었습니다.
작업 리뷰 기준으로 집계된 약 338건이 `git rev-list`로는 353건이었습니다.
`style.css` 줄 수도 9,037에서 멈춰 있었고 실제로는 10,174였습니다.

검수하는 쪽이 자기 문서의 숫자를 검수하지 않으면, 그 숫자도 결국 완료 보고와 다를 게 없습니다.
그래서 이 문서의 수치는 전부 저장소를 다시 클론해 커밋별로 되짚어 확정하게 했고,
재현 명령을 같이 적어 누가 다시 세도 같은 값이 나오게 해뒀습니다.

## AI가 원인을 잘못 잡은 두 번

검수는 결과물만 보는 것으로 끝나지 않았습니다. AI가 내놓은 원인 진단도 검수 대상이었습니다.
아래 두 건은 AI가 지목한 원인이 틀렸던 경우이고, 방향을 돌린 것은 제 쪽 관찰이었습니다.

### 8/10 가로 스크롤

> "index.html 전체 가로 스크롤이 생겼어. 원인 찾아줘."

전날 AI가 `html { overflow-x: hidden }`으로 덮어둔 상태였습니다.
원인을 없앤 게 아니라 증상만 가린 조치였는데, 그 상태로는 진단이 되지 않았습니다.
데스크탑에서는 이상이 없었는데 375 · 768 · 820 · 1024 · 1280과 실기기에서는 스크롤바가 그대로 나타났습니다.
가드는 안전망일 뿐 원인 제거가 아니라고 전날 적어뒀는데, 하루 만에 그대로 확인됐습니다.

원인은 접근성 요소였습니다.

```
<span class="a11y-hidden course-card__score">평점 5점 만점에…</span>
  → position: absolute
  → 캐러셀에 containing block(position: relative)이 없음
  → body 기준으로 잡힘 → 캐러셀 overflow-x 클리핑을 벗어남
  → 가로로 스크롤된 카드 위치(~2700px)가 페이지 scrollWidth에 그대로 더해짐
```

1024px에서 `scrollWidth`가 2644로 찍혔습니다.
두 캐러셀(`.course-list--slider` · `.magazine__list`)에 `position: relative` 한 줄을 넣어
절대요소를 안에 가두게 했더니 768 · 1024 · 1280에서 넘침이 0이 됐습니다.

이 건에서 배운 것이 세 가지였습니다.

- **접근성을 위해 넣은 요소도 레이아웃을 깨뜨릴 수 있습니다.** 화면에서 감추는 처리라고
  검증 대상에서 빼면 안 됩니다. 이번에는 그 요소가 넘침의 원인이었습니다.
- **임시로 덮어둔 가드는 원인을 찾기 전에 걷어내야 합니다.** 켜둔 채로는 증상이 안 보일 뿐 아니라
  측정값까지 왜곡됩니다. `body { overflow-x: clip }`은 `scrollWidth`를 clamp하기 때문에,
  끄고 재야 넘치는 지점을 좁힐 수 있었습니다.
- **어떤 속성이 통하고 안 통하는지가 그 자체로 단서입니다.** `overflow: hidden`은 소용없는데
  `position: relative`만 통했다는 것은, 절대요소가 상위 컨테이너 밖을 기준으로 잡혔다는 뜻이었습니다.

### 8/13 더블탭

> "링크를 두 번 눌러야 이동한다."

AI가 hover 가설을 세웠습니다. 터치 기기에서 첫 탭이 `:hover`로 소비된다는 가정이었고,
이 프로젝트에 `@media (hover)` 가드가 하나도 없다는 걸 근거로 들었습니다.
방어 코드를 두 번 넣었지만 두 번 다 눌러보니 그대로였습니다.

가설을 뒤집은 건 코드 밖에서 나온 관찰이었습니다.

> "GitHub Pages 링크로 열면 한 번에 이동해."

배포본에는 그 hover 가드가 하나도 들어가 있지 않은데 정상이었습니다.
로컬 개발 서버에서만 나던 증상이었고, 넣었던 방어 코드는 `git checkout`으로 걷어냈습니다.

AI 가설이 두 번 다 빗나갔지만, 그때마다 "여전히 그대로다"라고만 돌려준 것이
결국 답으로 가는 길이었습니다. 고쳤다는 보고를 그대로 받았다면 코드만 늘었을 것입니다.

```
08-10   증상이 안 보임 → 실제로는 있었다
08-13   증상이 보임    → 실제로는 없었다
```

두 번 다 코드에는 문제가 없었습니다. 확인 환경이 결과를 갈랐습니다.

AI는 자기 진단이 틀렸다는 것을 스스로 알아내지 못했습니다.
같은 가정 위에서 코드를 고치고 다시 완료로 보고했을 뿐입니다.
방향을 바꾼 것은 확인 조건을 바꿔본 쪽이었습니다.
가드를 끄고 다시 재라고 지시한 것, 배포본에서 직접 열어본 것 두 가지였습니다.
AI 협업에서 사람이 대신할 수 없는 몫이 여기라고 봅니다.

## 검수 도구의 한계

앞의 두 건은 확인 조건을 바꿔봐야 원인이 나온다는 얘기였습니다.
그러려면 확인에 쓰는 도구부터 어디까지 믿을 수 있는지 알아야 했습니다.

프리뷰 페인이 768 이하에서 레이아웃 뷰포트를 1560으로 고정해버려 모바일 실측이 안 됐습니다.
구조는 `getComputedStyle`과 `scrollWidth`, DOM 상태로 확인할 수 있었지만
패딩 침범이나 터치 같은 것은 배포본에서 따로 봐야 했습니다.

실제로 프리뷰에서는 1열로 나오던 통계 블록이 iOS에서만 3열로 깨진 적이 있습니다.
같은 날 반대 방향 오차인 더블탭 건도 발생했습니다.
한쪽은 도구가 못 잡았고, 다른 쪽은 도구가 없는 결함을 만들어냈습니다.

그래서 반응형 구간에는 배포본과 실기기를 따로 확인하는 절차를 붙였습니다.
프리뷰에서 정상이던 것 중 iOS에서만 깨진 건이 세 개 나왔습니다.
FAQ 검색 인풋의 우측 패딩 침범, 중점(`·`)이 안 넘어가는 것, 그리고 통계 블록 3열입니다.

AI 산출물을 검수하려면 검수에 쓰는 수단부터 어디까지 맞는지 알고 있어야 합니다.
그걸 모르면 "확인했다"는 말이 AI의 "완료했다"와 다를 게 없습니다.

## 정리하면

지적으로 끝나는 문제와 그렇지 않은 문제가 있었습니다.
404 링크는 경로 규칙 하나가 틀린 것이어서 지적 한 번으로 끝났습니다.
색상은 컴포넌트 수만큼 판단 지점이 있어서, 359건 안에 여러 번 지적하고 일괄 정리까지 했는데도 61건이 남았습니다.
지적은 이미 생긴 것만 잡습니다. 생기는 자리가 여러 곳이면 잡는 속도가 생기는 속도를 못 따라갑니다.

그래서 사람이 할 일은 지적이 아니라 지적이 필요 없게 만드는 쪽이었습니다.
164페이지까지 누락 0으로 간 항목들은 한 번도 지적한 적이 없습니다.
착수 전에 페이지 생성 템플릿에 넣어뒀기 때문입니다.
AI는 시킨 것을 할 뿐 빠뜨린 것을 알려주지 않으므로,
빠뜨릴 수 없는 구조에 넣는 편이 매번 잡아내는 것보다 확실했습니다.

또 하나는 틀린 것이 AI 산출물만이 아니었다는 점입니다.
AI의 완료 보고가 틀렸고, AI의 원인 진단이 틀렸고,
제 문서에 적힌 집계가 틀렸고, 확인에 쓰던 프리뷰가 틀렸습니다.
검수는 만들어진 것을 보는 일이 아니라, 맞다고 말하는 근거를 전부 의심하는 일이었습니다.

AI에 맡길 수 있느냐는 질문의 답은 여기 있습니다.
만드는 일은 맡길 수 있었습니다. 무엇이 맞는지 정하는 일과,
맞다고 말하는 근거를 검증하는 일은 맡길 수 없었습니다.
