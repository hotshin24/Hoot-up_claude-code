## 2. 검수는 두 층위로 돌렸다

**[1] 구현 중 실시간 지적** — 생성된 화면·코드를 보며 즉시 반려
**[2] 완료 보고 사후 대조** — AI가 쓴 작업 리포트를 실측치와 1:1 대조

두 번째가 이 프로젝트에서 가장 많이 잡아낸 층위입니다.
**보고서는 만들어진 것이 아니라 만들려고 계획한 것을 기술하는 경우가 있습니다.**

### 실제로 잡힌 것

| 보고 | 실측 | 검출 방법 |
|---|---|---|
| 할인 페이지 **16개 생성 완료** | 14개 | 파일 개수 카운트 |
| 세부 페이지 필터바 **32개 전체 제거** | 4개 누락 | 잔존 파일 목록 대조 |
| 신규 JS **4종 추가** | 실제 8종 | 파일 목록 대조 |

앞의 두 건은 **8개 반복 처리의 마지막 항목(요리·베이킹)이 빠지고 둘 다 완료로 보고**됐습니다.
개별 사고가 아니라 배치 작업의 실패 패턴으로 판단해, 이후 개수 검증을 고정 절차로 넣었습니다.

```bash
# 배치 작업 후 반드시 실행
ls category-*-earlybird.html | wc -l   # 기대값 8
ls category-*-event.html | wc -l       # 기대값 8
```

세 번째 건은 방향이 반대인 **과소 보고**입니다.
오류의 방향은 일정하지 않고, **보고와 실측은 대조해야 한다**는 점만 같습니다.

### 반려하지 않은 것도 기록했다

> "`main`이 모든 페이지에 필요한가?"
> → AI가 제시한 근거가 타당해 원안 유지

검수가 트집이 아니라 판단임을 남기기 위해, 지적하지 않기로 한 건도 함께 적었습니다.

## 5. 자기 집계도 검수 대상이다 — 세 번 세고서야 맞았다

**이 프로젝트에서 가장 값비싼 교훈입니다.**

남의 완료 보고는 매일 대조하면서, 정작 자기가 세던 수치의 기준은 한 번도 대조하지 않았습니다.

```
1차   131건   16진수만 집계
2차   180건   08-03, 기준을 두 축(16진수 + 브랜드색 rgb 표기)으로 상향 정정
      08-05  "180 → 0 해소"로 기록
3차   205건   08-13, 커밋별 소급 재집계
```

**08-05의 "0건"은 오기였습니다.**

| | 16진수 | 브랜드 `rgb()` | 합계 |
|---|---|---|---|
| 08-03 | 132 | 73 | **205** |
| 08-05 (정리 후) | 4 | **78** ↑ | **82** |
| 08-13 (현재) | 6 | 55 | **61** |

그날 처리된 것은 16진수 축뿐이고, 브랜드색 `rgb()` 축은 오히려 73 → 78로 **늘었습니다.**

원인은 명확합니다. **08-03에 "무엇을 셀 것인가"를 두 축으로 넓혀놓고,
결과 검산은 옛 기준 한 축으로 돌렸습니다.**
기준을 고치는 것과 그 기준으로 검산하는 것은 별개의 작업이었습니다.

같은 성격으로 커밋 수(약 338 → 실측 353)와 `style.css` 줄 수(9,037 → 10,174)도 어긋나 있었습니다.

**검수자가 자기 수치를 검수하지 않으면 그 수치도 결국 "완료 보고"와 같아집니다.**

이 문서의 모든 수치는 저장소를 다시 클론해 커밋별로 되짚어 확정한 값이며,
재현 명령을 함께 적어둔 것도 같은 이유입니다.

## 6. 원인은 코드가 아니라 관측 환경이었다 — 대칭 사례 두 건

### 08-10 · 가드가 실재하는 결함을 가렸다

> "index.html 전체 가로 스크롤이 생겼어. 원인 찾아줘."

08-09에 `html { overflow-x: hidden }`으로 막아둔 상태였습니다.
데스크탑에서만 안 보였고 **375 · 768 · 820 · 1024 · 1280과 실기기에서는 스크롤바가 그대로** 났습니다.

원인은 접근성 요소였습니다.

```
<span class="a11y-hidden course-card__score">평점 5점 만점에…</span>
  → position: absolute
  → 캐러셀에 containing block(position: relative)이 없음
  → body 기준으로 잡힘 → 캐러셀의 overflow-x 클리핑을 벗어남
  → 가로 스크롤된 카드 위치(~2700px)가 페이지 scrollWidth에 더해짐
```

1024px에서 `scrollWidth`가 **2644**로 측정됐습니다.
두 캐러셀에 `position: relative` **한 줄**을 넣어 절대요소를 가두자 넘침이 0이 됐습니다.

**세 겹입니다.**
① 접근성을 위해 넣은 요소가 반응형을 무너뜨렸습니다.
② 가드가 증상을 가려 데스크탑 검수로는 잡히지 않았습니다.
③ `overflow: hidden`은 안 먹고 `position: relative`만 먹힌 것 자체가 "절대요소 탈출 중"이라는 신호였습니다.

`body { overflow-x: clip }`은 `scrollWidth`를 clamp하므로 **가드를 켠 채로는 측정 자체가 왜곡됩니다.**

### 08-13 · 환경이 없는 결함을 만들어냈다

> "링크를 두 번 눌러야 이동한다."

`@media (hover)` 가드가 프로젝트에 전무하다는 점을 근거로 hover 가설을 세우고
두 차례 방어 코드를 넣었습니다. **두 번 다 "여전히 두 번 눌러야 한다"** 는 답이 돌아왔습니다.

결정적 관찰은 코드 밖에서 나왔습니다.

> "GitHub Pages 링크로 열면 한 번에 이동해."

배포본에는 hover 가드가 **하나도 적용돼 있지 않은데** 정상이었습니다.
더블탭은 **로컬 개발 서버에서만 나던 환경 아티팩트**였고, `git checkout`으로 원복했습니다.

```
08-10   증상이 안 보임 → 실제로는 있음
08-13   증상이 보임    → 실제로는 없음
```

**둘 다 원인은 코드가 아니라 관측 환경이었습니다.**
가설을 두 번 실패한 뒤 코드 밖을 본 것이 이 건의 유일한 해법이었습니다.

## 10. 결론

가장 크게 배운 것은 **일괄 정리로 닫히는 문제와 그렇지 않은 문제가 다르다**는 점입니다.

링크는 상환됐습니다. 3,389 → 573 → 193 → 0으로 내려가 다시 오르지 않았습니다.
경로 규칙은 한 번 고치면 재발하지 않는 종류였기 때문입니다.

색상은 08-05에 일괄 정리했지만 표기 형태를 바꿔 재유입돼 지금 61건입니다.
**매번 판단해야 하는 항목은 일괄 정리로 닫히지 않습니다.**
템플릿이나 린트 같은 구조를 만들지 않는 한, 페이지가 늘어나는 만큼 다시 쌓입니다.

이 프로젝트는 그 구조를 만들지 못한 채 마감했고, 그것이 결론입니다.

그리고 검수자 자신도 검수 대상입니다.
131 → 180 → 205. 세 번을 세고서야 맞았습니다.
**남의 보고를 대조하는 절차를 자기 집계에는 적용하지 않았던 것**이 이 프로젝트에서 가장 오래 걸린 발견이었습니다.
